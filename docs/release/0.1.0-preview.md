- **Release date:** 2026-11-11
- **Version:** 0.1.0 (preview)
- **Status:** preview of the workbench + four hardware-verified pilot builds
- **License:** MIT for the workbench code (`LICENSE`); engine patches follow
  their upstream licenses; game data and art are never distributed
- **Public mirror:** <https://github.com/KIRARITenshiChan/GalNX-public>
- **Development repository (private):** <https://github.com/KIRARITenshiChan/GalNX>

## 1. What GalNX is

GalNX is a workbench that ports PC visual novels to the Nintendo Switch by
**orchestrating existing engines** instead of writing another engine. It owns
the parts that are the same for every port — manifests, engine selection,
payload/romfs planning, self-contained NSP packaging and verification, batch
runs, evidence recording — and leaves rendering, scripting and audio to the
engine that already supports the game.

Two boundaries define the project:

- **Workbench vs runtime.** GalNX drives; the engine runs on the console. Engine
  fixes are shipped as patches against a pinned upstream commit, never as a
  private fork of the CLI.
- **Forwarder vs self-contained NSP.** 0.1 targets self-contained NSPs: the game
  data lives in the package romfs, so installing the NSP is enough to start the
  game. Forwarders are out of scope for this preview.

The three rfvp builds share the same `exefs/main` (6,385,492 B, sha256
`536531738648db31fc466a1913a2d4607081b79cc302c9ff2a904eb25623ba11`), so an

the runbook: `sdmc:/switch/rfvp/nv12_off.txt` (CPU RGBA path) and
`sdmc:/switch/rfvp/h264_sw.txt` (emulator CPU decode; must not exist on
hardware).

## 4. Getting started (workbench)

Requirements: Windows 10/11, Python ≥ 3.11. Building NSPs additionally needs
devkitPro (`switch-dev`, `switch-portlibs`), Rust + devkitA64 for the rfvp
backend, and the FFmpeg nvtegra build described in
`docs/builds/045-nvdec-probe.md`. Running builds also needs the console keys
for packaging (`prod.keys`), which stay outside the repository.

```bash
git clone https://github.com/KIRARITenshiChan/GalNX-public.git
cd GalNX-public
pip install -e .
galnx doctor                      # environment check
galnx preflight --manifest examples/templates/minimal-manifest.yaml
```

A new port starts from `examples/templates/minimal-manifest.yaml`. The
`examples/pilot0*` manifests are real records kept for reproducibility, not
templates.

Build contract in one paragraph: the manifest is the only source of execution
configuration; `build.commands` and `build.artifact` are declared together;
`galnx build run --dry-run` prints the exact commands, working directory,
timeout and environment variable names (values masked) and never spawns a
process; `--yes` skips the interactive confirmation; a manifest without
commands reports `not_configured` and exits 3 rather than pretending success.
Engine descriptors only carry identity, version, patches and capabilities —
they never drive a build.

## 5. Requirements and compatibility

- **Host:** Windows only in 0.1.x. The build helpers (`scripts/build_nsp_game.sh`,
  `scripts/build_nsp_demo.sh`) call Windows tools through the devkitPro MSYS2
  shell; CI runs the portable subset on `windows-latest`.
- **Python:** 3.11+ (CI uses 3.12), dependencies `PyYAML`, `jsonschema`.
- **Toolchain (only when building):** devkitPro devkitA64 + switch-dev +
  switch-portlibs, CMake/Ninja, Rust nightly-2026-02-01 + devkitA64 target,
  MSYS2 bash.
- **Console:** retail Switch with Atmosphère (sigpatches) for unsigned
  homebrew; NSP installation via DBI MTP/FTP. Firmware/Atmosphère versions are
  not pinned in 0.1.

## 6. Evidence and verification levels

Every claim in the repository is tagged with one of:
`source_review`, `build_verified`, `emulator_verified`,
`device_verified`, `game_verified`, `partial`, `in_progress`,
`unknown`. An emulator result never counts as hardware evidence, and an
engine-level result never counts as game-level acceptance. The matrix is the
single source of truth for game acceptance; `docs/builds/` holds the numbered
build records and hashes.

## 7. Licensing and redistribution

- Workbench code: **MIT** (`LICENSE`).
- Engine patches under `docs/builds/patches/`: distributed under each
  upstream license (rfvp MPL-2.0, krkrsdl2 MIT, Kirikiroid2-NX KiriKiri
  BSD-style non-SPDX, ONScripter GPL-2.0-or-later).
- The rfvp runtime statically links an FFmpeg configured with `--enable-gpl`
  (NVDEC decoders require it), so **a distributed NSP is GPL-2.0-or-later as a
  whole**. GalNX does not publish NSPs; if you redistribute a build, provide
  the corresponding sources and build scripts. The decision and evidence are
  recorded in `docs/release/tasks/TASK-LICENSE.md` and
  `docs/third_party/inventory.yaml`.
- Game data, Chinese localisation files, fonts, screenshots and covers are
  third-party material; they are not in the public tree and must be sourced by
  the user from their own copy.

### 8.1 Post-review fixes (2026-11-11)

After the first public snapshot, an external review asked for six changes; all six
are in this preview line: non-interactive `build run` / `batch build` are now
fail-closed without `--yes` (exit code 2, `EOFError` treated as a decline),
`examples/quickstart/` is a runnable build example wired into CI, game-level
verification levels were re-aligned with the evidence (Pilot-04 is
`device_verified`), a project that declares `build.commands` without
`build.inputs` no longer reads or writes the cache, and the public snapshot was
regenerated and re-scanned. See `docs/release/tasks/FIX-01.md`,
`FIX-02.md`, `FIX-03-FIX-05.md`, `FIX-04.md` and `docs/release/expert-review-0.1.0.md`
§12.

## 9. Public snapshot

The public mirror is a sanitized snapshot of the private development
repository, published per release event. Each snapshot commit message
(`Public snapshot of private commit <sha>`) names the private source commit it
was generated from; `PUBLIC_RELEASE.md` inside the snapshot records the file
count, byte count and exclusion count generated by
`scripts/public_release_sanitize.py`. See `docs/environment/public-release.md`
for the policy, the publication log and the reproduction steps.
